## 0. Abstract

요즘 GPT나 Gemini가 사용자이력을 활용해서 LLM을 개인화하려고 하지만, 개인화를 체계적으로 평가할수 있는 방법은 충분하지 않아 개인화를 평가할 수 있는 BESPOKE라는 벤치마크를 제안한다고 함.
이 벤치마크를 사용하면 응답을 평가할때 단순 선호점수만 반환하는게 아니라 시스템에 대한 세밀한 진단을 담은 피드백도 제공해준다고 함.

## 1. Introduction

RAG를 통합한 LLM은 전통적인 검색시스템에 비해 훨씬 유용하고 편리하지만, 여전히 일률적인 정보를 주는 경향이 있음.

GPT나 Gemini같은 요즘 LLM들은 저런 기능들을 부여하고있는 추세이지만 이런 방법론들을 평가하고 진단해줄 평가방법은 잘 뒤따라오지 못해 개인화 벤치마크의 필요성이 높다고 함.

## 2. Related work

**RAG LLM**

RAG를 평가하는 벤치마크는 대부분 QA에 대한 응답의 사실성을 판단하는 형식을 사용함.
RAG-QA는 QA에서도 긴 답변을 평가하지만 특정 분야에 국한되어있다는 한계가 있으며, Search Arena는 다양한 도구를 다루는 오픈도메인 평가이고 사실성보다 답변의 선호도를 평가하지만 역시 개인화된 평가를 제공하지는 못한다는 한계가 있음.

**개인화된 LLM**

사람이 만든 가짜페르소나를 이용하거나, LaMP-QA처럼 커뮤니티 데이터를 사용한 시도가 있었으나, 앞서 언급했듯이 데이터의 도메인이 매우 제한적임.
따라서 여러 도메인에 걸친 현실적인 사용자 기록을 사용하고, 이 기록을 통해 정확한 정보요구를 도출하는것이 좋은 개인화시스템을 만드는 데 필수적임.

## 3. Constructing BESPOKE

<figure style="width:36%; margin:0 auto;">
  <img src="/assets/img/ai_paper_reviews/BESPOKE/bespoke-fig3.png" alt="논문 Table 2: BESPOKE 통계 - 사용자 30명, 세션 2,870개(검색 2,153, 채팅 717), 사용자당 평균 95.67세션" style="width:100%;">
</figure>

BESPOKE는 3주간 30명의 다양한 사용자들에게서 검색세션 2153개, 채팅세션 717개를 사용해 인간주석 방식으로 데이터를 수집했다고 함.

### 3.1 Task formulation

개인화 과제를 형식적으로 나타내면
사용자는 $$u$$, 질의는 $$q$$이고 사용자의 검색이력 $$\mathcal{S}_u$$과 채팅이력 $$\mathcal{C}_u$$을 합친 사용자이력을 $$\mathcal{H}_u=\{\mathcal{S_u},\mathcal{C_u}\}$$ 라고 할 때, $$q,\mathcal{H}_u$$를 받아 사용자가 진짜 획득하길 의도한 정보 $$n_q$$ 를 추론해 그 의도에 맞는 응답 $$r$$을 생성하도록 하는것.

### 3.2 Human annotator & History collection

human annotator는 다양성이 높도록 선발했고, 검색은 Google, 채팅은 Gemini를 사용했다고 함.

### 3.3 Human annotation pipeline

BESPOKE 데이터의 task 카테고리는 개인화가 중요한 영향을 미치는 분야라고 판단된 분석, 가이드, 추천, 설명분야로 한정했는데, Search arena의 task 분류에서 영감을 받은것이라고 함.

![논문 Figure 2: BESPOKE 구축 과정 개요 - 기록 수집, 질의와 정보 요구 주석, 응답-판정 쌍 주석, gold rubric과 gold information 구성, 테스트 시 응답 평가](/assets/img/ai_paper_reviews/BESPOKE/bespoke-fig4.png)

전체 파이프라인은 위와 같은데, 인간주석데이터 생성절차는 크게 3가지의 단계로 구성됨.

<div style="display:flex; gap:12px; background:rgba(135,131,120,0.15); padding:16px 20px; border-radius:8px; margin:16px 0;">
<div>💡</div>
<div markdown="1" style="flex:1; min-width:0;">

1. 질의 $$q$$와 사용자의 진짜 의도인 정보요구 $$n_q^+$$ 작성.
2. 출력된 $$k$$개의 응답들 각각에 대해 점수 $$s$$ 와 피드백 $$f$$ 작성 (R-J 쌍)
3. 이상적인 응답 $$r^+$$를 수동으로 생성

</div>
</div>

1. $$k$$개의 응답을 만들때는 $$q$$ 하나를 넣고 여러개의 응답을 뽑는방식이 아니라 $$q$$로부터 $$(k-1)$$개의 가상의 정보요구 $$n_q^-$$를 만들어서 $$(q,n_q)$$를 입력하고 응답 $$r$$를 출력받음.
그리고 이 응답들에 대한 피드백을 작성할때는 Need alignment, Content depth, Tone, Explanation style 이 4가지 기준에 대해 채점함.
2. 이상적인 응답 $$r^+$$를 만들때는, AI가 생성하고 사람이 점수와 피드백 매기고 하는걸 5점짜리 응답이 나올때까지 반복함.

### 3.4 Evaluation

이제 그렇게 만든 인간주석데이터를 LLM 모델 평가에 사용해야함.
인간주석데이터를 별도의 평가용 LLM에 쥐어주고 대상 LLM에서 생성된 응답을 채점하도록 자동화함.
채점은 사실성과 개인화품질두가지로 나뉨.

**사실성** 

응답이 정답정보를 잘 포함했는지를 확인함.
먼저 이상적인 응답 $$r^+$$를 잘게 쪼개서 검증가능한 원자적 정답들의 집합 $$\mathcal{I}_q^+=\{i^+_{q,1},...,i^+_{q,n}\}$$ 으로 수동으로 나누는데, 이때 검증가능하고 사실인 주장들만 남겨놓는다고 함.
그래서 대상 LLM이 생성한 응답을 $$\hat{r}$$이라고 하면 저 원자적 정답들을 $$\hat{r}$$이 얼마나 잘 담고있는지 평가 LLM $$\mathcal{E}_r$$가  확인하고, $$Recall(\hat{r})=\vert I_r\vert/\vert I_q^+\vert$$ 로 계산됨.

**개인화품질**

먼저, 아까 사람이 만든 R-J 쌍 예시를 보여주고 평가 LLM $$\mathcal{E}_p$$가 그 채점방식을 흉내내게 만듦.
구체적으로는, $$\mathcal{D}_q=\{(r_i,s_i,f_i)\}^m_{i=1}$$ 이렇게 m개의 R-J쌍 예시를 few-shot으로 넣어주고, 채점기준표인 golden rubric $$R^+_q$$를 만들게 함.
그 다음 그렇게 만든 채점기준표를 $$(s,f)=\mathcal{E}_p(\mathcal{D_q},\mathcal{R}_q^+,n_q^+,q,\hat{r})$$ 진짜 정보욕구, 질문, 대상모델의 응답과 함께 평가모델에 넣어서 점수와 피드백을 생성하도록 함.

## 4. Experiments

검색기능이 켜진 GPT, Gemini, Perplexity 등 6개 프론티어 모델들의 사실성과 개인화품질을 BESPOKE 벤치마크를 통해 평가해봄.

### 4.1 Meta evaluation

근데 이 BESPOKE의 가장 큰 약점이, 과연 R-J쌍을 보고 사람처럼 평가하도록 의도한 LLM $$\mathcal{E}_p$$가 실제로도 그렇게 잘 작동하는가? 임

그래서 여기서는 안쓴 R-J쌍 300개로 $$\mathcal{E}_p$$의 성능을 측정했고, 베이스라인으로는 w/o Personal, w/o Feedback이랑 비교함.
w/o Personel은 평가용 LLM에 R-J쌍을 안주고 일반적인 평가기준에 대한 정의만 띡 준거고, w/o Feedback은 R-J쌍을 주긴 하는데 J에 피드백 $$f$$은 안주고 점수 $$s$$만 준거임.

$$\mathcal{E}_p$$가 의도대로 잘 작동하는지 보기 위해 $$\mathcal{E}_p$$가 출력한 점수 $$s$$, 피드백 $$f$$을 평가하는데, 점수는 숫자이기때문에 피어슨 상관계수와 스피어만 상관계수로 평가하고, 피드백은 정성적으로 평가해야하므로 LLM as Judge 방법으로 인간의 피드백과 모델이 출력한 피드백이 동일하다고 볼 수 있는지 분류하게 한다고 함.

그렇게 실험해본 결과, 개인화를 고려한 평가기가 훨씬 인간의 평가와 비슷하다는 결과가 나왔고, 점수와 피드백을 모두 포함한 $$\mathcal{E}_p$$가 가장 좋은 점수를 보임으로서 R-J쌍을 보여주면 진짜 사람처럼 평가하나? 라는 의문에 대한 정당성을 확보함.

### 4.2 Effect of user context

![논문 Table 4: History Usage, Query Awareness, History Selection, User Context 설정에 따른 검색 증강 LLM 6종의 평가 결과](/assets/img/ai_paper_reviews/BESPOKE/bespoke-fig7.png)

여기서는 사용자맥락을 모델에 제공할때 사용자 기록 $$\mathcal{H}_u$$를 어떻게 사용하는게 가장 좋을지 실험해봄.
물론 벤치마크입장에선 저런건 평가받는 LLM이 알아서 할일이지 알빠노? 해도 상관없지만 친절하게 해준듯.

History usage : 사용자 맥락을 사용하는것이 좋은게 맞나?
Query awareness : 사용자 맥락을 질문을 보고 동적으로 만들지(✅) 질문을 안보고 정적으로 만들지(❌) 
History selection : 전체기록을 줄지(❌) 질문에 관련된 기록을 줄지(✅)
User context form : 사용자 기록을 압축해서 프로필형태(Profile)로 줄지 사용자 기록 그대로 줄지(Raw)

사용자 기록 $$\mathcal{H}_u$$을 넣어서 좋은 응답을 출력하는게 목표라고 생각했는데 갑자기 profile 이야기가 나와서 당황...
근데 profile은 사용자기록을 압축해서 진짜 프로필 형태로 넣어주는거라 모순되는 이야기는 아니라고 함.

결과를 보면 질문을 보고 동적으로 질문에 관련된 기록들로 프로필을 만들어주는 방식의 사용자 맥락이 가장 효과적인 조합이었다고 함.

### 4.3 Feedback as a diagnostic signal

![논문 Figure 3: 최저·최고 성능 설정에서 GPT-4o-search 응답과 BESPOKE의 점수·피드백 비교 - 피드백이 개인화 품질 차이를 짚어 줌](/assets/img/ai_paper_reviews/BESPOKE/bespoke-fig11.png)

BESPOKE를 사용했을때, 이 벤치마크는 점수만 띡 주는게 아니라 실제로 LLM의 약점과 개선점을 잘 진단해주는 피드백을 제공한다는 사실을 보여줌.

### 4.4 Effective method for history retrieval

사실 History selection을 할때 어떤 기록이 질문과 관련이 있는지는 LLM(GPT-5)를 써서 검색했는데 이건 실험에서나 가능하지 현실적으로는 불가능한 방법.
그래서 효과적인 검색기를 써야되는데,  단순 질문 $$q$$를 가지고 사용자기록을 검색하면 너무 성능이 떨어져서 CoT Expansion이나 Pseudo-history처럼 질문을 확장하는 방식을 쓰는것이 훨씬 효과적이라고 함.

### 4.5 Impact of web-search quality on personalized responses

개인화 과제가 잘 해결되지 않는 이유를 확인하기 위해 golden information, 즉 이상적인 검색내용을 직접 모델에 먹여봄으로서 일종의 검색에 대한 ablation을 해봤는데, 이때 조금씩 다 성능에 향상이 있었지만 추론모델이 비추론모델에 비해 훨씬 큰 성능향상이 있었다고 함.
즉, 최적의 개인화를 달성하기위해서는 정확한 검색능력과 높은 추론능력이 둘다 필요하다는 이야기

## 0. Abstract

LLM한테 API 사용법을 가르쳐서 Agent로 만드려는 시도들과 성과들은 있었는데, 당시 SOTA인 GPT-4를 써봐도 자꾸 API를 제대로 못써서 호출을 실패하는등의 미숙한점이 많았다고 함.
그래서 자기들은 RAG와 fine-tuning을 결합한 Gorilla라는 모델을 만들었고, 이렇게하면 API를 잘 못쓰는 문제점도 상당히 해결될 뿐 아니라 방대한 양의 API를 사용하는 능력을 갖게 되면서도 훈련 이후에 API가 업데이트되어도 적응할 수 있다는 엄청난 장점이 있음. 확실히 Toolformer보다도 훨씬 더 쓸모있어진 모델같음

## 1. Introduction

기존 도구 사용방법론들처럼 컨텍스트 내에 쑤셔넣는방법으론 더이상 많은 API들을 학습시킬수없다고 지적함.
그래서 자기들은 self-instruct 파인튜닝과 retriever을 이용해 API문서를 보고 API를 선택할수 있는 능력을 길러줄거라고 함.
근데 저자 자기들도 도구를 쥐여줘서 LLM을 유용한 웹 에이전트로 만드니 어쩌니 하다가도, 정작 진짜 필요한 일반적인 Restful API를 다루는 agent가 아니라 ML API라는 AI모델 저장소에서 모델을 호출하도록 설계함… 😡
HuggingFace, TensorHub, TorchHub에서 ML API 호출을 수집하는데, 사실 이렇게 하면 우리가 생각하는 유용한 웹툴도 아닐뿐더러 모델을 내려받고 로컬에서 돌려야하기때문에 사용성은 최악일거임.
솔직히 RestAPI가 더 어렵고 데이터구하기도 어렵고 채점도 어려우니까 못한거일듯

모델카드는 이런식으로 모델을 소개해놓은 quick start 같은건데, 허깅페이스를 예로 들면 모델은 20만개가 넘지만 대부분은 모델카드가 없거나 하는 식으로 관리가 안돼있어서 각 도메인에서 상위 20개의 모델만 선택했다고 함.
멀티모달 데이터 7개 도메인, 컴퓨터 비전 8개, 자연어 처리 12개 이런식의 다양한 도메인에서 모델을 20개씩 골고루 뽑았고, 그렇게 1645개의 모델이 모임.

이제 저 모델들의 모델카드를 스크래핑하고 파싱해서 

```
{domain : ..., framework : ..., functionality : ..., api_name : ..., api_call : ..., api_arguments : ..., environment_requirements : ..., example_code : ..., performance : ..., description : ...}  
```

이런식의 필드를 갖는 API json객체로 변환함.
한 모델카드에서 여러개의 API json객체를 뽑아낼수도 있을것같은데 그냥 한 모델당 한 API json객체만 뽑아내서 1645개의 모델에서 그대로 1645개의 파싱된 형식의 API 객체를 뽑았다고 함.

  <figcaption style="text-align:center; font-size:0.85em; color:gray;">

그렇게 만든 API를 GPT4로 Self-Instruction방식으로 뻥튀기하기위해 이런식으로 few-shot용 예시를 만듦. HuggingFace, Tensorhub, Torchhub 각각에 대해 6개씩 사람이 직접 만들었고, 그중 3개를 랜덤으로 골라 few-shot으로 넣어줌.
하나의 &lt;Reference API&gt; 당 10개의 instruction - output pair(User - Assistant) 부분이 만들어져서 총 16450개의 데이터가 만들어짐.
&lt;Reference API&gt;, 즉 API json하나에서 instruction(input) ← API json → output 이렇게 만들어지는데, 그러면 API json과 안맞는 엉뚱한 instruction이나 output이 만들어지는건 아닌가 우려됐음.
가령 API json은 ViT에 관한 문서인데 갑자기 감정분석을 해달라는 instruction을 해달라거나…
근데 API json을 보면 domain, description등의 필드가 있어서 그거보고 엉뚱한 질문을 생성할 확률은 낮음.
그리고 output도 이상한 틀린문법만들수도 있지 않나했는데, 마찬가지로 API json에 api_call, example_code등 사실상 치팅시트가 있어서 그럴확률은 낮다고 함.
다만 실행이 실제로되는지는 확인하지 않기때문에, 저게 진짜 100% 맞는데이터는 아니라고 고백.

### 3.3 Verifying APIs

![논문 Figure 4: AST sub-tree 매칭 - Gorilla가 낸 API 호출 트리가 데이터셋 API 트리의 부분 트리인지 비교해 채점](/assets/img/ai_paper_reviews/Gorilla/gorilla-fig7.png)

모델의 성능을 평가하기 위해 저자들은 AST 매칭이라는 방법을 사용하는데, Sementic한 정확성을 따지기 위해 테스트케이스가 아니라 이 방식을 사용했다고 함.
그래서 ‘아니 Sementic한 정확성을 따질려면 오히려 테스트케이스를 써야하는거 아닌가? 이미지분류를 하고싶다는 입력이 들어오면 ResNet도 맞고 DenseNet도 맞고 ViT도 맞고 다 복수정답인데 하나만 정답처리한다고??’ 했는데, 생각해보니까 Retrieve-Aware버전의 일반 Gorilla모델은 Retriever가 input에 맞는 API json을 가져오는데 거기에 모델이 적혀있어서 엉뚱한 모델을 쓰면 기능은 해도 오히려 틀렸다고 판단하는게 맞음.

물론 이건 Retriever가 잘못 문서를 가져와버리면 모델은 잘못한거 없는데도 틀렸다고 판단되기때문에 이런 억울함을 해소하고자 뒤에서 Oracle Retriever를 이용한 실험도 한다고 함.

그렇지만 Zero-shot버전은 여전히 억울한게 맞음.
아무 API json 문서도 없으니까 진짜 자기들입장에선 복수정답을 인정해줘야하는데, 이걸 좀 해소해주기 위해서 모델이 너무 많아서 선택지도 많은 HuggingFace에서는 API 이름이틀려도 도메인만 맞으면 정답으로 인정해준다고 함.

그리고, 정확도와 할루시네이션을 구분해서 채점하는데, 틀린 API를 호출했지만 트리에 있는 호출이라면 정확도는 내려가지만 할루시네이션이라고 판단하지는 않음.
근데 트리에 존재하지도 않는 호출이라면 정확도뿐만 아니라 할루시네이션점수도 깎임.

## 4. Evaluation

Gorilla가 다른 베이스라인들에 비해 얼마나 우수한지, retriever의 종류가 모델에 어떻게 영향을 주는지를 보고, API문서가 변경되었을때 강건하게 잘 작동하는지도 확인함.

베이스라인으로는 GPT-4, GPT-3.5 Turbo, Claude-v1, LLaMA-7B을 사용함.
Retriever로는 BM25, GPT-Index, Oracle retriever(가상)가 있음.

BM-25는 TF-IDF같은 고전적인 통계기반 키워드매칭방식이라고 함.
그리고 GPT-Index는 임베딩모델인줄알았는데, 그게 아니라 저건 그냥 라이브러리고, text-davinci-003이라는 그냥 LLM을 엔진으로 써서 하나하나 읽어보고 관련문서를 찾는 retriever로 사용한듯…
RAG에서 임베딩을 사용하는 방식이 표준적인 방식은 맞지만, 이런 LLM검색같은 다른방법도 있다고 함

### 4.1 AST Accuracy on API call

![논문 Table 1: Torch Hub, HuggingFace, TensorFlow Hub API에서 LLM과 retriever 조합별 정확도, 환각률, 오류율](/assets/img/ai_paper_reviews/Gorilla/gorilla-fig8.png)

우선 zero-shot 설정으로 실험을 진행함.
참고로 Table1에서의 Gorilla(0-shot)는 zero-shot 버전으로 학습된 Gorilla고, 나머지 Gorilla는 Retrieve-Aware 버전으로 학습된 Gorilla에 retriever를 사용한것임. 
zero-shot 버전으로 학습된 Gorilla에 retriever사용한거 아님! 그건 Table2에서 나옴
zero-shot버전의 비교결과를 보면, Gorilla zero-shot버전이 자기보다 훨씬 큰 다른 모델들을 압도적인 성능차이로 이겼음.

![논문 Table 2: retrieval 기법 비교 - retriever 없이 학습한 Gorilla와 Oracle retriever로 학습한 Gorilla에 추론 시 각 retriever를 썼을 때](/assets/img/ai_paper_reviews/Gorilla/gorilla-fig9.png)

다음으로 zero-shot버전의 Gorilla에 retriever를 썼을때의 실험결과는 Table2에 나와있는데, 이 표가 아무설명이 없어서 해석하기가 진짜 난해함. 
첫 행인 Gorilla with retriever 이 부분은 fine-tuning시에 어떤 버전으로 모델을 훈련시켰는지이고, 두번째 행인 zero-shot ~ Oracle은 추론시점에 어떤 retreiver를 사용했는지를 나타내는것임.
확인해보면, zero-shot 버전으로 학습된 Gorilla에 retriever를 사용하면 성능이 심각하게 하락하는것을 확인 할 수 있음.

마지막으로 Retrieve-Aware 버전의 모델이 얼마나 성능이 좋은지도 확인했는데, zero-shot버전의 Gorilla에 비해 Oracle을 사용하는 Retrieve-Aware 버전의 모델의 성능이 훨씬 더 높은것을 확인 할 수 있음.
그러나, 사실 Oracle retriever라는건 실제로 추론에서는 쓸수가 없는 이상적인 retrieve이므로, 현실적인 retriever를 사용하면 사실 zero-shot 버전의 Gorilla에서 retriever 없이 쓰는게 더 성능이 높음.

근데 임베딩기반 retriever같은 제대로된것도 하나도 안써보고 저딴소리하는게 이해가 안감…
그리고 참고로 논문에 수치를 실험 데이터와 틀리게 적어놔서, 수치도 거르면서 봐야됨…
